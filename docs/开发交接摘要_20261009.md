## 1. 项目目标与用户最新决定

项目结合适用培养方案、个人学业与认定、个人需求和当期开课信息，提供可解释、可调整的选课方案。首版范围是规划、比较、调整、保存和导出，学生在学校官方平台完成实际选课；不自动执行选课。

职责保持明确：RAG 检索适用依据并提供出处；Agent 组织对话及工具调用；确定性程序负责学分、门数、资格、时间冲突和排课计算。先把基础数据与计算跑通，再接入 RAG 和对话；真实页面适配在取得可验证样本后推进。

本次对话的重要纠偏，按发生顺序记录：

1. 最初要求按原交接优先级完成 P0 数据导入和规则计算，再做 P1 显式模拟课表；优先沿用工作区技术栈、目录和运行方式。
2. 已开始部分代码后，用户要求先理解课程与项目，明确暂停急于编码。现有代码留下作为草稿，本轮没有继续实现业务功能。
3. 学校选课平台与学生档案尚无本项目可用的统一 OpenAPI。可以先用已知字段设计、独立模拟数据验证；不能称为已接入全量学校数据。
4. Excel 用于理解学生身份、培养审核、已修/在修、成绩与认定字段。此前“真实用户必须上传 Excel”的定位已纠正；不能从当前参考样本推定运行时上传入口。
5. 用户确认未来按基本信息检索本人档案，再输入偏好并针对性检索，最终给出答案。实际档案来源和检索接口尚未设计；当前样本不能证明这个能力已实现。
6. 用户要求建立统一开发进度文档，并同步此前开发。每轮开发和验证更新 [开发进度](开发进度.md)，历史测试和当前验收分别记录。
7. 已授权根据培养方案 PDF、Excel 和真实选课截图初步设计字段，成果是 [字段字典](数据结构与字段字典_v1.md)与[系统模块矩阵](系统模块与数据来源矩阵_v2.md)，不是数据库 DDL 或代码迁移。
8. 最新增加登录权限要求：使用前须验证学校身份。知道他人姓名或学号不能查询他人的个人信息。方向修订为：**学校身份登录 → 可信本人学生绑定 → 本人档案检索 → 偏好 → 针对性检索 → 答案或方案**。
9. 本轮完成权限设计和交接后，建立本地 Git 仓库及关联 GitHub 私有仓库，新的对话再进行代码开发。

## 4. 模块和字段设计结论

五个业务模块：M1 学生档案与适用性，M2 培养要求，M3 学业与认定，M4 课程/开课/个人选课，M5 需求与方案。三项支撑：S0 来源与版本，S1 确定性计算，S2 登录与权限；后续增加 F1 RAG/Agent。

关键语义必须延续：

- 方案版本、专业、入学年、修读路径与外语层级保留适用范围，未知不默认通过。个人要求和通用培养方案独立，当前三份 2026 级方案不能直接绑定给样本学生。
- 原 23 条候选继续待审核；项目内核对可执行、官方规则地位、对学生适用是不同属性。新增可执行演示规则另存并标 DEMO/synthetic。
- 字段值、原文、定位、观察时间、数据快照及映射版本分别保存；来源冲突保留各方陈述，不能用最后一次读到的值覆盖。
- 课程 CourseDefinition、代码关系 CourseCodeLink、教学班 Section、时段 Meeting、考试 ExamArrangement 分开。括号代码可记录同一标题中的身份关系，不自动建立跨来源学分互认。
- 修读行观察 AcademicObservation 不直接等于一次 AcademicAttempt；同代码多次修读、跨要求重复显示、替换关系分开。体育三条同代码不同成绩不能一律折叠成一次；缺少实例与可重复获分依据则待确认。
- 学分、门数、学时、记点及二三四课堂分账。认定覆盖多个条件不重复增加实际学分；来源要求中的学分不自动成为已获学分。
- 在修、通过、不通过、被替代、待认定分开；备选志愿、页面已选、正式中选、保存方案和已获学分分开。
- 余量可为负数，已知零与未知分别保存；周次、班号、校历或先修内容缺失不以模拟值补齐。
- PreferenceSet/ConstraintItem 与 PlanVersion/ValidationResult 保存版本。修改偏好保留锁定和固定安排，重新计算；冻结方案引用所用数据与规则版本，不能将旧结果当作当前状态。

字段字典是逻辑设计，小对象可以嵌套，不要求一对象一表。`data_kind` 描述来源；新增 `data_scope` 与 `owner_student_id` 描述访问范围，不能由客户端声明权限。StudentPlanBinding 是培养方案适用绑定，StudentIdentityBinding 是认证身份绑定，二者不能混用。

## 5. 登录权限设计交接

权限设计已保存，**尚未实现登录、学校认证或安全验收**。主链路是：有效会话 → 服务端验证主体 → 可信学生绑定 → 本人资源集合 → 指定对象及关联资源。

学生访问范围来自服务端 AuthContext。输入他人学号、修改 student_id 或猜到 saved_id、snapshot_id、source_id，都不能改变身份；读取、修改、保存、导出、来源文件和后续检索均检查归属。创建个人对象时服务端赋所有者，数据库查询带本人条件；不能返回全库后由前端过滤。

学校账号和密码的验证优先在学校实际支持、获准接入的认证入口完成。本项目不存学校密码、不建立学校密码哈希库；具体协议、应用资格、回调配置及可信学号属性尚未确认。学校官方说明给出了应用申请接入步骤，不能预设个人项目已经获得接入。认证和档案/学业数据获取分别处理，学校登录成功不等于已有档案 API。[浙江大学统一身份认证服务说明](https://its.zju.edu.cn/tysfrzwgr/list.htm)

官方接入尚不可用时，开发可采用显式 mock 认证验证授权逻辑，但只连接 synthetic 主体和数据；mock 默认关闭、仅开发环境开启，不验证学校密码，也不在学校认证失败后自动降级为成功路径。不能据此宣称完成真实学校登录。

匿名用户没有个人资料访问权限；资料维护角色可维护公共培养/课程资料，不自动获得任意学生成绩权限。会话到期、退出与撤销由服务端落实，原始个人文件、导出和缓存同样受保护。RAG/Agent 接收限定的本人上下文，不能成为权限决策者。

## 7. 优先修复的问题

完整问题表在 [开发进度](开发进度.md)。新对话先检查下列事项：

1. **登录与个人隔离缺失**：`Application.demo/constraints` 全局共享；`/api/bootstrap`、`/api/saved` 和 `frozen_result(saved_id)` 未限定本人；SQLite 表没有 owner。当前 Origin/Host 校验不是认证。先落实服务端身份上下文和个人所有权，再允许多用户或真实个人记录。

3. **计算语义**：负余量不能拒绝；同课程代码多修读不能统一去重；个人替换、跨类认定与修读实例待核对；适用专业、方案版本及有限数值保护需完善。
4. **时间与版本**：考试冲突未实现；真实周次/班号不足；旧方案载入与当前数据校验、重启后的活动数据选择尚未联调。
