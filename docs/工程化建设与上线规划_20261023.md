# 浙大教务助手：工程化建设与上线规划

更新：2026-10-23。这是下一阶段的建议方案，**尚未实施或部署**。展示网页的未来规划以本文件为主，旧版体验优化清单作为历史参考。重点是把本机可运行的系统逐步建设成可部署、可管理、可恢复、可测量的服务，不用技术名词替代工程结果。

## 1. 当前基础与目标

当前已有原生网页、Python HTTP 服务、SQLite 持久化、服务端本人身份绑定、会话失效与撤销、带归属的对话/请求/运行记录，以及 AcademicHarness、来源版本与确定性计算。对话存储和权限并不是从零开始。学校连接、部分任务状态和草稿仍依赖进程内存；已有记录保存也不等于跨设备历史、生产多用户管理和故障恢复已完整实现。

当前运行仍是本机 v34 后端，前端包含 2026-10-23 的加宽布局与居中首页输入框。Redis、生产应用服务器、PostgreSQL、多进程工作队列和公网教务服务均未接入；没有已验证的用户容量、QPS、可用性或恢复时间指标。

| 建设方向 | 具体工程产物 | 完成后需要拿出的证据 |
|---|---|---|
| 网站部署 | 可复现镜像、生产启动入口、域名/HTTPS、环境配置、健康检查 | 从干净环境部署成功；版本、配置和回滚步骤可核对 |
| Redis 与并发治理 | 限流、并发配额、有界队列、派生缓存、任务租约 | 压测下不串用户、不无限堆积；超时、重试和故障行为可预测 |
| 账号与权限 | 账户生命周期、可信学校身份绑定、会话管理、配额与审计 | 登录/过期/撤销/越权测试通过；管理权限不默认授予成绩访问权 |
| 对话持久化 | 历史分页、消息顺序、运行恢复、请求幂等、归档与删除策略 | 刷新与重启后记录一致；重复提交不重复写入或改方案 |
| 发布工程 | CI、环境分离、数据库迁移、制品版本、灰度与回滚 | 同一制品从测试到生产；失败发布能恢复，数据迁移可兼容 |
| 可观测性与成本 | 分阶段指标、关联日志、告警、模型/学校调用预算 | 能定位学校慢、模型慢、排队慢或数据库慢，而非只看到总耗时 |
| 数据生命周期 | 备份、恢复演练、保留期限、私有文件存储与删除链路 | 可恢复到可说明的时间点；删除覆盖派生索引与后续备份策略 |
| 可靠性与容量 | 超时、熔断、有界重试、取消、依赖替身与分级负载测试 | 依赖故障不放大为雪崩；容量结论有负载、延迟、错误率与成本依据 |

## 2. 部署：从可运行到可重复上线

先分开两个交付：**静态项目介绍站**只展示经过确认的文案与素材；**可登录的在线教务服务**运行真实认证、学校查询和模型调用。前者可以独立推进，不能据此声称后者已上线。此包只为制作网页提供材料，没有执行任何公网发布。

生产服务先补适配层，把当前 HTTP handler 的路由和请求上下文接到合适的生产 WSGI/ASGI 入口；不能把启动命令直接换成某个服务器就声称兼容。Python 官方说明 `http.server` 不适合生产使用。[Python 官方文档](https://docs.python.org/3/library/http.server.html)

初期采用单主机、少量服务的版本化容器部署即可：反向代理负责 HTTPS、请求大小、连接/超时设置；应用负责认证和业务；数据库与私有资料使用持久卷。配置与密钥通过部署环境注入，不写进镜像或前端。保留应用版本号、配置版本、数据库版本、存活与就绪检查。SSE 需要验证代理缓冲、连接中断、心跳和排空旧连接。Docker Compose 的生产配置分层可作为单机起点。[Docker 官方文档](https://docs.docker.com/compose/how-tos/production/)

上线门槛还包括域名、证书续期、可信 Host/Origin、CSRF、Cookie 策略、依赖网络可达性和学校允许的认证/数据路径。本机本人客户端已登录，不证明同一方式可以直接放到云服务器；该依赖应先验证，再决定服务器位置或本人连接桥接方案。学校侧授权与网络问题未解决前，可以先交付介绍站和部署环境验证。

## 3. 账号：应用身份、学校身份与会话分层

沿用服务端验证身份的原则：内部用户 ID、学校主体标识与绑定版本分别维护。输入姓名或学号不授予数据权限。若引入应用账户，可先评估受邀登录或合适的身份提供方，再定义账户注册、停用、重新绑定、退出所有设备和删除申请；不把某种注册方式预先写成已选定方案。

每次读写对话、资料、方案、导出和缓存都检查 owner、realm 与有效绑定。运维管理员可查看运行健康和配额，不默认查看学生成绩与完整对话。应用会话需考虑登录后轮换、空闲/绝对过期、撤销传播、Secure/HttpOnly/SameSite 等 Cookie 设置，并验证撤销后旧标签页与排队任务的行为。[OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

学校密码、Cookie 和 Token 继续仅在学校连接的内存中，不放进 Redis、数据库、队列消息或日志。Redis 可以保存应用侧短期会话元数据或连接归属引用，但不是学校凭据共享仓库。多进程初期可按本人连接固定路由到持有它的进程；该进程退出时提示重新认证。真正跨实例接管需要单独的认证与连接设计，不能靠复制内存对象完成。

重新登录后的历史访问要区分“本人已有记录的读取授权”和“当前学校连接的有效性”。设计明确的重新授权与历史归属规则后，才开放跨会话历史；历史来源显示原取得时间，新问题需要最新事实时重新查询，不能为了显示旧聊天而取消现有认证代次或来源检查。

## 4. 对话：数据库保存事实，队列推进任务

复用现有 SQLite 存储与仓储边界，逐步补齐逻辑对象：用户/绑定、会话、对话、消息、运行、来源版本、方案 revision、附件引用。逻辑对象不强制一对象一表，也不为展示关系图立即拆完现有 JSON 结构。明确三类内容：用户可见聊天记录、供模型使用的有界上下文、用于排障的运行诊断；它们的读取权限和保留期限分别定义。

消息按对话内单调序号排序并设置唯一约束，历史用游标分页，查询索引至少覆盖 owner/realm/时间或对话序号。用户可逐步获得重命名、归档、检索、导出和删除入口；移动端/跨设备草稿作为后续功能，先约定保存周期与过期行为。

一次请求的建议落库过程：

1. 客户端提交请求 ID；服务端校验归属、请求摘要及当前方案 revision。同一 ID 携带不同正文应拒绝。
2. 同一数据库事务保存用户消息、待运行记录与待投递 outbox 事件；避免“写库成功但未入队”丢任务。
3. 工作进程领取任务，执行前再次检查用户授权、连接归属和当前版本；每个对话只允许一个会改变方案的活动运行，其他请求有明确排队/拒绝策略。
4. 完成时以事务保存助手答复、最终运行状态与方案版本；成功状态在提交后对外可见。进度流与最终持久结果分开。
5. 服务重启后核对遗留 pending/running，区分未执行、已提交、失败和结果未知。重复投递读取已有结果，不重复写入消息或修改方案。

幂等写入不等于外部模型调用“恰好一次”。如果供应商已处理请求而本机在写入前断线，费用和结果可能未知；需要记录阶段、提供有限重试政策，并承认不能保证零重复计费。取消也只承诺停止后续可控步骤，不把无法撤销的已发出请求说成已撤回。

## 5. Redis：解决明确的共享状态与并发问题

Redis 的目标是治理负载与协调任务，不是自动让学校接口或模型供应商变快。优先顺序为：先测量瓶颈，再做限流/并发控制，再决定是否需要队列和缓存。

| 用途 | 建议设计 | 关键边界和验收 |
|---|---|---|
| 限流与配额 | 用户、学校连接、全局供应商三级速率/活动任务上限；原子更新与 TTL | 多实例不能各算各的；Redis 异常时受控拒绝新昂贵任务，不能失效后无限放行 |
| 有界队列 | 限制待处理长度和等待期限，区分交互查询与较长资料处理；公平调度 | 队列满时给可理解的状态；不让一个用户占满全部工作进程 |
| 任务可靠投递 | Redis Streams 消费者组、确认、租约、重试上限和失败队列，与数据库 outbox 配合 | 数据库提交成功后再确认；进程宕机/重复投递可恢复。Pub/Sub 不承担持久聊天或唯一任务记录 |
| 对话并发控制 | 唯一持有者的短租约，加数据库 revision 校验/栅栏版本 | 租约过期后的旧工作进程不能覆盖新结果；不把 Redis 锁当成唯一正确性保障 |
| 派生结果缓存 | owner/realm/授权版本/来源 hash/查询条件/算法版本进入缓存键 | 只缓存可重建派生数据；不跨用户命中，不用旧缓存冒充本轮学校最新数据 |
| 进度与连接归属 | 短期运行状态和学校连接所属进程引用 | 凭据仍留内存；进程消失后撤销归属并重新认证，不自动转交凭据 |

Redis 官方提供限流模式；Streams 支持消费者组、确认与重放，可以作为队列候选，但应用仍需实现事务边界和失败恢复。[Redis 限流](https://redis.io/docs/latest/develop/use-cases/rate-limiter/)、[Redis Streams](https://redis.io/docs/latest/develop/use-cases/streaming/)

易丢弃缓存与不可随意淘汰的协调/队列数据要分开配置资源及保留策略；仅用不同 key 前缀或逻辑库，不足以隔离实例级内存淘汰影响。Redis 自身的持久化、恢复与资源告警也必须验收。先允许单实例方案，不为架构图提前承诺集群高可用。

## 6. 存储、备份与数据生命周期

先测量 SQLite 写锁等待、事务时长和实际写入并发；优化事务范围、索引和连接管理。达到明确的多进程写入/运维需求后，再评估 PostgreSQL，配套连接池、迁移脚本、回填核对、兼容期与回滚方案，不把更换数据库等同于业务正确性提升。

原始私有 PDF、附件和派生索引单独存放；在线化后可使用私有对象存储，数据库保存归属与内容摘要，下载仍需本人鉴权，不能暴露服务器物理路径或永久公共链接。记录来源取得时间、hash、schema/解析器版本与质量状态，来源结构变化时能定位受影响的答案与索引。

备份必须覆盖数据库、文件引用关系和恢复所需配置；密钥有独立受控恢复路径。先确定可接受的数据丢失窗口 RPO 和恢复时间 RTO，再执行恢复演练、检查记录数/归属/附件一致性，不能只以“备份任务成功”作为完成。PostgreSQL 官方将 SQL 导出、文件级备份与连续归档列为不同备份方式，选型取决于恢复目标。[PostgreSQL 官方文档](https://www.postgresql.org/docs/current/backup.html)

对话、诊断日志、来源材料、派生缓存和备份分别定义保留期限。删除流程覆盖正文、附件、索引与缓存；备份中的历史副本按已约定保留期自然淘汰，并防止恢复时复活已删除账号。具体天数和服务指标需要后续确定，本规划不伪造现有承诺。

## 7. 发布、监控与依赖可靠性

**CI/CD 与变更管理。** 开发/测试/生产环境分离，测试使用合成夹具和可控接口替身；真实学校账号与个人资料不进入 CI。流水线覆盖关键权限隔离、消息幂等、版本冲突、来源契约、迁移兼容和媒体/前端构建检查。制品带源码 hash，按环境注入配置；先小范围试点，观察后放量。数据库变更优先兼容旧应用版本，应用回滚与数据恢复分开演练。供应商 SDK/依赖有锁定与升级策略，基础镜像和密钥轮换有维护责任人。

**可观测性。** 用 request_id/run_id 串起请求、工具、学校、模型和数据库阶段；默认日志记录状态、时长、错误分类、版本与计数，不记录密码、完整个人正文或来源文件。指标区分排队等待、首个可见状态、最终答复延迟、学校/模型调用耗时、数据库锁等待、修复/重试率、取消率及单次请求成本。告警覆盖队列积压、错误率、学校会话失效、模型余额/预算、磁盘与备份失败。p50/p95 与错误率必须标明时间窗、负载和样本量。

**依赖可靠性。** 分别设置连接/读取/整体运行超时；对可重试错误使用有上限的退避与抖动，避免前端、服务端和队列层同时重试放大调用。学校或模型故障时熔断新请求并逐步探测恢复，给用户明确状态。不能降级成虚构 Agent 回答，也不能把旧来源当作当前查询结果。对会改变方案状态的步骤结合 revision 检查，不以重试修复覆盖冲突。

**成本与容量管理。** 为本人、试点群体和全局配置模型预算、活动运行数和请求大小/附件上限；计量来源、模型、检索和计算成本。模型路由若将来扩展，需按能力、费用与质量验证，不擅自改变当前仅 Flash 的运行设置。

## 8. 分阶段推进与验收

| 阶段 | 交付内容 | 验收门槛 |
|---|---|---|
| D0 展示发布准备 | 简洁介绍页、当前架构、工程规划、经确认可公开的素材 | 静态资源/移动端/原图入口可用；公开范围单独确认；无需收集学校密码 |
| E1 可重复部署 | 生产入口适配、镜像、环境配置、HTTPS、健康检查、部署手册 | 干净环境可部署，学校认证路径明确，版本可查，应用可回滚 |
| E2 用户与持久状态 | 账号生命周期、本人隔离、历史分页、幂等与重启恢复 | 两用户互不可见；同一请求重复/断线/重启不损坏消息与方案版本 |
| E3 并发与任务治理 | Redis 限流/有界队列/租约、派生缓存与故障降级 | 逐级负载报告、过载行为、Redis/工作进程故障恢复证据完整 |
| E4 受控试点运维 | 监控告警、成本配额、备份恢复、灰度与发布回滚 | 有责任人、运行手册、恢复演练和试点反馈，再评估扩大用户范围 |

容量测试先用学校/模型替身覆盖 1、5、10、20 个并发运行等拟议档位，再按结果调节。分别统计在线连接数、活动请求数和吞吐率；不能将某档测试通过写成真实用户容量。真实学校与付费模型只在获准范围和预算内验证，不能拿真实接口做无上限压测。报告包含固定机器/版本、任务比例、数据大小、运行时间、p95、错误率、队列长度和成本，阈值在测试前约定。

阶段表示依赖关系，不是工期承诺。优先交付可部署和可恢复的最小服务，再用实测决定扩容或数据库迁移。

## 9. 对话体验作为持续维护

现有答复准确性、简洁性、条件继承和来源约束继续维护；完整语义、正式培养适用与正式推荐仍需单独验收。页面不恢复已移除的过程/依据面板。本次路线图仅将这些项目放在持续维护位置，展示重点转向工程化能力；降低展示篇幅不意味着这些业务边界已解决。
