# 浙江大学选课助手：推荐能力线规划入口

日期：2026-10-13。用途：承接当前长对话，在新对话先形成推荐能力线的规划、设计方案和执行方案。本文记录最新产品范围及已核验状态，不表示新的推荐功能已经实现。

## 1. 用户最新决定：最终目标不变，先推进推荐能力线

用户明确的最终体验：

> 每个学生登录之后，系统获取学生相关信息，包括专业、年级，匹配对应培养方案；学生通过系统主体 Agent 提出选课推荐问题，系统结合 RAG 给出解释和多个课表推荐选择。

最终流程为：学生登录 → 可信本人绑定及获授权的资料取得 → 适用培养方案匹配 → Agent 对话澄清目标、硬条件与偏好 → 检索依据、查询课程及确定性计算 → 多套推荐及取舍说明 → 连续对话调整、比较、保存与导出。学生自己在学校官方系统选课，系统不自动执行。

**最新范围决定：学校学生信息系统目前没有可用接入渠道，学生接入线暂缓；下一对话先对推荐能力线给出规划、设计和执行方案。** 不把完成学校认证或个人源接入作为设计工作的前置，也不把暂缓写成取消最终个性化目标。本次不是继续编码、采集或调用模型的指令。

两条线的边界：

| 主线 | 最终职责 | 当前安排 |
| --- | --- | --- |
| 学生接入线 | 学校认证、可信学生绑定、专业/入学年/培养类型/方向/路径、学业修读与成绩、认定、当前正式选课及来源许可 | 暂缓真实接入；保留输入契约和未知依赖，不预设学校协议/OpenAPI，不收集学校密码 |
| 推荐能力线 | 理解选课需求、检索适用依据、选择候选课程/班次、计算约束、提供多个有差异的方案、解释和多轮调整 | 下一对话的规划重点；使用已有数据和现有计算/Agent基础设计可分步实施的完整流程 |

只有专业、年级通常不足以判断“本人还缺什么”。设计应分别表示方案/路径、学业进度、已选固定项和偏好；缺失时输出可支持的参考建议及必要澄清，不能默认未修过、已满足先修或符合毕业要求。用户手动选择的方案可作为获准参考范围，不等于可信本人绑定。

## 2. 产品方向核对：避免将子模块做成最终产品

原始需求的四个问题是：我还缺哪些要求；接下来适合修什么；本学期如何组成可行课表；为什么这样推荐、改条件会怎样。见原 inputs 的 ANALYSIS.md 第2、4、5节及 CODEX_HANDOFF.md 八项验收。

当前采集、去重、RAG设计均服务于原目标，没有取消 Agent 主入口。但如果后续只做培养方案问答、全量文档加工或模型对比，会偏离用户要的推荐体验。下一轮须从用户场景倒推技术工作，并把RAG检索效果和推荐业务效果分别验收。

- Agent负责理解、澄清、组织工具和解释；表单只辅助核对，不把手动合成预览称为Agent理解。
- RAG提供培养要求、课程说明和政策依据；结构化工具查询课程/班次/观察事实；确定性程序负责学分、资格、时间冲突与方案校验。
- 多个回答应围绕多个有意义的选择和理由，不能只生成几段措辞不同的文字。多套课表需有实际课程/班次差异及明确取舍。
- 可以设计“培养要求优先、兴趣优先、时间安排优先”等方案方向，但这只是待设计示例，不是用户固定要求的三种策略。可行解不足时不凑数量。
- 不必精细处理全部162份方案、全部29类要求或所有特殊路径后才验证首个场景。首片范围由场景决定；后续扩大覆盖另验收。
- 原八项及新增权限未覆盖部分继续未完成，不能用数据量、文档数量、测试数量或检索命中率替代完整产品验收。

## 4. 已有真实数据与保留的缺口

### 4.1 采集范围与两种路线

用户先要求浏览器工具与后端只读请求分别取得样例，为未来比较保留事实基础。浏览器课程采集因效率问题按用户要求停止，已完成过程复盘；后端完成最终要求范围。两路线原件、回执、失败/中断及停点均保留，未完成最终效率对比报告。下一轮不必继续比较作为推荐设计前置。

用户已明确现有秋冬样例够用，不要求全年开课。跨类（专业）、搜索引擎、研究生课程为用户排除采集范围；荣誉/补考在观察范围内为空。不要恢复这些采集，也不要把春夏或多账号采样设为前置。用户说明总体课程池共享，专业相关板块可能随专业变化；板块是出现关系，不等于互斥课程集合或本人适用规则。

## 5. 下一对话应交付什么

**先交付规划、设计方案和执行方案，不直接开始实现。** 建议围绕以下六项形成可审阅成果，而不是继续堆叠通用架构文档：

1. **需求与范围基线。** 对照原四个问题/八项验收及本次最新范围，明确推荐能力线首版的输入、输出、非目标和最终学生接入点；把本人结论、参考场景和synthetic测试分清。
2. **完整用户流程。** 选一个代表方案/目标学期及对话场景，设计需求澄清、候选课程、多个具体课表、理由/依据/取舍和连续调整；覆盖无解、只有一解、缺数据以及有冲突的请求。不要把方案查询页当最终产品。
3. **推荐架构与数据契约。** 说明Agent、RAG、结构化查询、要求计算、排课搜索、排序和统一复核各自职责；设计当前如何提供参考场景输入、未来如何替换为可信本人上下文。不得把用户填写学号或选择方案当认证，也不规定必须上传Excel/截图。
4. **RAG与推荐算法方案。** 沿用v2中有效的分块/引用/范围/版本约束；确定实际场景需要的章节与课程说明、课程身份映射、候选召回、硬约束/软偏好、多方案差异与排序解释。给出词法/Embedding/混合的引入时点和衡量价值的方法，不把向量库或特定模型当先决条件。
5. **阶段执行方案。** 列每个阶段要复用/修改的现有模块、输入依赖、产物、验证和继续条件。RAG v2 S1–S3是可复用基础，需嵌入完整推荐主线；不必先处理全部专业。真实班次缺周次时明确允许展示和禁止断言的内容，synthetic校历不补入真实记录。
6. **验收与依赖清单。** 同时包含数据/引用准确性、Agent需求理解、多方案有效性与差异、偏好与锁定继承、三态/无解、可复现版本及权限；检索评估与推荐业务评估分开。分别列现在可做、只需局部核对、需要用户决策、需学校渠道的事项。

可使用的代表对话示例来自原需求：“优先补专业选修，偏向AI，尽量周五没课，保留体育课”，随后“周五必须空闲，其他锁定项保持”。这个示例不是对当前用户学业、兴趣或可选资格的事实认定。新设计可选更贴合已有数据的场景，并说明选择原因。

当前数据足够支持设计和本机受限参考检索，尚不足以保证真实本人完整排课。未来若要做“真实参考资料＋显式假设场景”的独立试验，应设计独立用途授权、来源和结果标识，不能直接把真实数据塞进固定A/B mock。选择方案/输入条件是场景设置，不能冒充学校学生档案。

## 6. RAG v2应复用的内容与调整点

- 全部资料登记与用途/适用过滤，先授权后取回/评分，返回前及引用回查时重新核验；不先全库top-k再过滤。
- 精细章节/课程行/跨页表头/附注及页级适用；混合页按条款分范围，二三四课堂暂缓不删除同页普通课程。
- 来源、清理、分块、语料、索引和策略版本独立；候选/冲突/unknown保留，更新不静默覆盖旧结果。
- 50题蓝图与95候选定位均是machine_seed_unreviewed，gold=0。人工标注另存；开发/保留组冻结，不能由模型自答自评称人工验收。
- 检索实验固定同一语料与题目，先建立可解释基线，再比较向量/混合。模型生成与Embedding是不同接入决策。
- 调整点：S1–S3是支撑模块，下一版执行方案还须明确它们怎样接入候选课程、确定性排课与多方案解释；不能仅以问答命中结束阶段目标。
- 原v2建议的5方案/50题和数值门槛是设计目标，不是已经达到，也不应成为任意最小原型的机械前置。缩小首片时须说明验收分母和未覆盖范围。
